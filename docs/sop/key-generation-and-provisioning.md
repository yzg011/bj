## 1. Overview

Key material on the camera originates from three independent paths. There is
no single key store or key-generation daemon: each path uses the mechanism
appropriate to its lifetime — hardware OTP for immutable device keys, writable
configuration storage for regenerable keys, and read-only verified images for
build-time anchors.

| Path | When | Generated by | Key material |
|---|---|---|---|
| **A. First-boot provisioning** | Once per device, at first application start | Vendor provisioning build of `otp_mfg`, driven by `fw/app/init/app_init.sh` | Content-protection (CP) key region in OTP |
| **B. On-device generation / derivation** | Every application start; on owner binding / factory reset | Application key-management module (`cp_key_manage.c`) over `/dev/hwrng` and SHA-256 | OTP application root key + IV; configuration keys `conf_key_1`, `conf_key_2`; TLS session keys |
| **C. Build-time injection** | Firmware build on the build host | Pre-generated key files in the build environment (`build_security_image/`) | Image-encryption AES key (`crypto_key.bin`), RSA boot-chain key pairs, application public key (see `certificate-inventory.md`) |

## 2. Entropy infrastructure

- **Hardware TRNG**: SoC-internal true random number generator at device-tree
  node `trng@188a0100` (`compatible = "realtek,rts3917-trng"`, dedicated clock
  `trng_ck`).
- **Kernel driver**: `drivers/char/hw_random/rts_rng.c` registers the generator
  with the Linux **hwrng** framework (Kconfig `HW_RANDOM_REALTEK`), which
  exposes it as the character device `/dev/hwrng` and feeds the kernel entropy
  pool.
- **Conditioning** (per driver source): the raw entropy source is selectable
  (digital, analog, or both XORed); output passes a **von Neumann
  conditioner**, and each 8-byte result is XOR-mixed with kernel
  `get_random_bytes()` output before delivery.
- **Userspace APIs**:
  - Key generation on the device reads `/dev/hwrng` directly (open + read) —
    this is the only custom randomness API used by the application
    (`get_random_bytes()` in `cp_key_manage.c`).
  - Library DRBGs in the firmware (TLS stacks) are seeded from the kernel
    entropy pool via `/dev/urandom` / `getrandom()`; the ultimate source is the
    same TRNG.

## 3. Key material generated or derived on the device

| Item | How it is produced | Mechanism / API | Storage | Consumer |
|---|---|---|---|---|
| **OTP application root key** (32 B) + IV (16 B) | Generated on-chip at first application start from the hardware RNG | `get_random_bytes()` → `otp_mfg -w --ecc <hex> 48` / `... 240`; burn-once (skipped when the OTP lock flag is set) | OTP: data offset 48 = AES key slot #1 (hardware group 2); data offset 240 = general-purpose region (`otp-memory-structure.md` §3/§4) | Hardware AES engine via the OTP key-load path (§5); key bytes are never exposed to software |
| **Content-protection (CP) key region** | Generated inside the vendor provisioning build of `otp_mfg` at first boot | `otp_mfg --cp_write` → `--cp_lock` (permanent lock), driven by `app_init.sh`; region layout is vendor-defined | OTP general-purpose segment (0x0A0+), locked after programming | Vendor content-protection components |
| **`conf_key_1`** — configuration encryption key (32 B key + 16 B IV) | Generated on-chip from the hardware RNG when absent | `get_random_bytes()` (64 B) → AES-256-CBC wrap → file write; unwrapped in memory on subsequent boots | `/conf/conf_key_1` (writable configuration storage), stored encrypted | `key_manage_encrypt/decrypt_with_conf_key_1()` — encryption of `/conf/cpplus/` configuration data |
| **`conf_key_2`** — owner-binding configuration key (32 B key + 16 B IV) | Derived, not random: `key = SHA-256(seed)`, `IV = SHA-256(seed + "_IV")[0:16]`, where the seed is the owner-binding SHA-256 obtained from the vendor cloud (`thing.home.owner.sha256`) | SHA-256 KDF (`cp_sha256`) → AES-256-CBC wrap → file write (updated only if the derived value differs) | `/conf/conf_key_2`, stored encrypted | `key_manage_encrypt/decrypt_with_conf_key_2()` (chunked 32 KiB CBC) |
| **TLS session keys** | Produced by the TLS library DRBG during each handshake | Library DRBG seeded from the kernel entropy pool (`/dev/urandom` / `getrandom()`) | RAM, per session | Vendor cloud / P2P TLS channels |

Factory reset (`cpty_sys_reset_default`) deletes `/conf/conf_key_1` and
`/conf/conf_key_2`; both are regenerated on the next start — `conf_key_1`
randomly from the hardware RNG, `conf_key_2` from the owner binding.

## 4. Key configuration flow (detailed)

```
(power-on)
    |
    v
[Stage 1 - First boot: fw/app/init/app_init.sh]
    |  otp_mfg --cp_verify
    +-- OK --------------------------------------------> (continue to Stage 2)
    |  fail  (fresh device)
    v
    otp_mfg --cp_write     <-- CP keys are generated inside the vendor
    |                          provisioning build of otp_mfg
    v
    otp_mfg --cp_lock      <-- CP key region permanently locked
    |
    v
    otp_mfg --cp_verify --- fail ---> reboot -f   (fail-closed: the
    |  OK                            application starts only after
    |                                verified provisioning)
    v
[Stage 2 - Application start: key_manage_init()  (daemon main)]
    |
    +-- try_create_root_key():
    |     OTP group-0 flag: lock bits set? --- yes ---> skip (burn-once)
    |        | no
    |        v
    |     /dev/hwrng --> 32 B key --> otp_mfg -w --ecc @ data offset 48
    |     /dev/hwrng --> 16 B IV  --> otp_mfg -w --ecc @ data offset 240
    |
    +-- create_conf_key_1():
    |     /conf/conf_key_1 --- exists ---> unwrap (AES-256-CBC) --> load
    |        | absent
    |        v
    |     /dev/hwrng --> 64 B (32 B key + 16 B IV)
    |        --> wrap (AES-256-CBC) --> write /conf/conf_key_1
    |
    +-- conf_key_2():
          /conf/conf_key_2 --- exists ---> unwrap --> load into RAM
              | absent  (created later, on owner binding)
              v
          key = SHA-256(seed)               seed  = owner-binding SHA-256
          IV  = SHA-256(seed + "_IV")[16]          from the vendor cloud
              --> wrap (AES-256-CBC) --> write /conf/conf_key_2
    |
    v
[Stage 3 - Runtime key use]
    /conf/cpplus/ configuration data  <-- conf_key_1 / conf_key_2 (AES-256-CBC)
    pre-provisioned device info       <-- key-wrap decryption at start
    TLS session keys                  <-- TLS library DRBG <-- /dev/urandom
    OTP root key --> rts_otp_load_aes_key() --> hardware AES engine
                     (ekey mode: key never visible to software)

[Stage 4 - Mount time: fs_mgr]  (independent of Stage 2/3)
    OTP group-0 flag byte (mask 0x02) set?
    +-- no  --> key from SD card (provisioning path):
    |           /media/sdcard/ipcam_crypto.bin
    +-- yes --> key from fstab key_loc = /etc/keys/crypto_key.bin
                 |
                 v
         dm-crypt "aes-cbc-plain64" mapping
```

Step summary:

1. **CP provisioning (fail-closed)** — on the first boot the init script
   verifies the OTP CP key region; on a fresh device it is programmed and
   permanently locked, then re-verified. Any verification failure reboots the
   device instead of starting the application.
2. **Root key burn-once** — at the first application start a 32-byte root key
   and a 16-byte IV are drawn from the hardware RNG and written into dedicated
   OTP slots (the write is skipped once the OTP lock flag is present).
3. **Configuration keys** — `conf_key_1` is created from the hardware RNG if
   absent; `conf_key_2` is derived by SHA-256 from the owner binding once the
   device is bound. Both are stored AES-256-CBC-wrapped and loaded into memory
   at every start.
4. **Consumption** — configuration encryption, device-info decryption, TLS
   session establishment, and (via the OTP key-load path) hardware AES.
5. **Mount-time data decryption** — `fs_mgr` selects the partition decryption
   key according to an OTP flag byte and builds the dm-crypt mapping.

## 5. Mechanisms and APIs reference

| Layer | Mechanism / API | Role in key generation / configuration |
|---|---|---|
| Kernel | hwrng framework → `/dev/hwrng` character device | True-random byte source for on-device key generation |
| Kernel | Entropy pool — `/dev/urandom`, `getrandom()` | Seeds library DRBGs (TLS session keys, general PRNG use) |
| Kernel | nvmem framework → `/sys/bus/nvmem/devices/rts-otp0/nvmem` | OTP status/flag reads (provisioning state, lock flags) |
| User space | `otp_mfg` CLI — `-r`/`-w` with `--ecc` (ECC bytes auto-placed per group), plus vendor provisioning commands `--cp_verify` / `--cp_write` / `--cp_lock` | OTP read/write and first-boot CP key provisioning |
| Kernel | `rts_otp_load_aes_key(index)` — "ekey" mode of the Realtek crypto driver (a caller passes an all-zero key whose last byte selects the OTP slot) | Loads an OTP-resident AES key straight into the hardware AES engine; key bytes never appear in CPU-visible memory |
| Application library | `cp_aes` (software AES-256-CBC), `cp_sha256` (KDF) | Wrapping of stored configuration keys; derivation of `conf_key_2` |
| Application library | `key_manage_*` API (`cp_key_manage.h`, libcp_core) | Uniform key lifecycle: create/load/delete, per-key encrypt/decrypt entry points |
| Kernel / user space | dm-crypt `aes-cbc-plain64` (driven by `fs_mgr`) | Partition data decryption at mount time |
| TLS libraries | wolfSSL / mbedTLS DRBG | TLS session key generation for cloud / P2P channels |

## 6. Build-time key material (not generated on the device)

- **Image-encryption key**: `crypto_key.bin` (32-byte AES-256 key) and
  `crypto_iv.bin` (16-byte IV) are pre-generated files in the build
  environment (`build_security_image/crypto_key/`). `genimage_encrypt.sh`
  encrypts the kernel, root filesystem, and application images with
  AES-256-CBC using this material, and the same key ships inside the root
  filesystem at `/etc/keys/crypto_key.bin` so that `fs_mgr` can decrypt the
  partitions at mount time (Stage 4 of the flow above).
- **Boot-chain and application public keys**: the RSA key pairs used for FIT
  and partition-signature verification and the Ed25519-class application
  public key are generated outside the device during firmware development and
  are deployed only as public verification keys inside verified, read-only
  images. Their inventory, purpose, and locations are documented in
  `certificate-inventory.md` (§2, items C1–C5).

## 7. Protection properties

- **OTP-resident keys**: write-once-then-lock. The CP region is programmed at
  first boot and permanently locked; the application root key write is skipped
  once the OTP lock flag is present. OTP AES keys are consumed through the
  key-load path of the crypto engine, so the key bytes are never readable by
  software.
- **Fail-closed provisioning**: application startup is gated on successful
  verification of the provisioned CP keys (failure ⇒ reboot instead of start).
- **Stored configuration keys**: `conf_key_1` / `conf_key_2` are written to
  `/conf` only in AES-256-CBC-wrapped form and are deleted by factory reset,
  after which they are regenerated.
- **Build-time anchors**: verification keys live inside dm-verity-protected or
  signature-verified images, so modifying them breaks verification at the next
  boot or mount (`certificate-inventory.md` §5).

## 8. Glossary

| Term | Meaning |
|---|---|
| TRNG | True random number generator (SoC-internal hardware entropy source) |
| hwrng | Linux hardware-random framework; exposes a hardware RNG as `/dev/hwrng` and feeds the kernel entropy pool |
| nvmem | Kernel non-volatile-memory framework; exposes OTP as a sysfs device |
| ekey | "Efuse key" mode of the Realtek crypto driver: an index byte selects an OTP AES key slot to be loaded into the hardware engine |
| CP keys | Content-protection keys provisioned into a locked OTP region by the vendor manufacturing tool |
| KDF | Key derivation function; here SHA-256 over a binding seed |
| Key wrapping | Encrypting a key with AES-256-CBC before persisting it |
| dm-crypt | Kernel device-mapper target providing block-level decryption (`aes-cbc-plain64` in this product) |
| fs_mgr | User-space mount manager applying `/etc/fstab.user` (verify/key options) |
